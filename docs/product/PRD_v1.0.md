# AI Customer Service Copilot — PRD v1.0

**产品名称：** AI Customer Service Copilot  
**产品类型：** AI 电商客服与商家运营辅助平台  
**目标版本：** MVP v1.0（Sprint 2）  
**产品负责人：** 待填写  
**文档状态：** 初稿，待原型设计与验收  
**目标周期：** 约 1–2 周

## 1. 产品背景

现有 AI 客服原型已支持商品咨询、订单查询、物流查询和投诉信息收集。

Sprint 1 针对商品检索失效、工单编号不一致、错误业务承诺等问题进行了优化。在固定的 36 条演示评测案例中，规则通过数由 15 条提升至 36 条。该结果仅反映本地固定样本，不能作为真实商用准确率。

然而，现有产品依然存在两项核心缺陷：

- 投诉工单只存在于单次回复中，没有数据库持久化与后续状态管理。
- 商家无法查看咨询量、问题类型和待处理投诉，缺少运营反馈工具。

因此，本轮目标是在现有 Agent 基础上补全工单管理和基础运营分析能力。

## 2. 目标用户

### 2.1 买家

主要需求：

- 快速了解商品信息及订单物流。
- 在 AI 无法解决问题时记录售后诉求。
- 获取真实、可追踪的投诉编号。

### 2.2 商家客服人员

主要需求：

- 查看买家提交的投诉。
- 了解投诉内容及关联订单。
- 更新处理进度，避免遗漏。

### 2.3 商家运营人员

主要需求：

- 查看咨询量和主要问题类型。
- 识别待处理投诉及常见咨询问题。
- 根据客服数据改善服务流程与商品说明。

以上需求为当前产品假设，尚未经过真实商家访谈验证。

## 3. 产品目标与非目标

### 3.1 核心目标

构建一条可演示、可追踪的业务流程：

**买家咨询 → AI 自动处理 → 无法解决时创建工单 → 商家处理工单 → 运营概览查看结果。**

### 3.2 本轮非目标

不实现多店铺 SaaS、多平台接入、真实退款执行、自动赔付、复杂权限系统、真实人工实时聊天或商业支付功能。

## 4. 功能需求

### FR-01：客服问答与投诉入口（已有功能，局部修改）

**描述：** 保留现有商品、订单、物流和政策问答流程。

当用户提出投诉或需要进一步处理的问题时，系统应能够识别诉求并创建工单。

**关键要求：**

- AI 不得凭空承诺退款已到账。
- 无法获取订单信息时，应明确提示用户补充必要信息。
- 投诉编号由业务程序生成，而非由 LLM 编造。
- 只有工单真正写入数据库后，才能提示“已成功记录”。

### FR-02：工单持久化管理（P0）

**用户故事：**

作为商家客服人员，我希望能够集中查看买家投诉，并更新处理进度，以便跟踪问题是否得到处理。

**功能要求：**

1. 投诉成功后生成唯一工单编号。
2. 将工单编号、投诉摘要、关联订单、状态和时间保存至 SQLite。
3. 支持查看工单列表与工单详情。
4. 支持按状态筛选。
5. 支持填写处理说明并更新状态。
6. 浏览器刷新或服务重启后，历史工单仍然存在。
7. 对同一请求的重试避免重复创建工单。

**状态定义：**

- `open`：待处理
- `in_progress`：处理中
- `resolved`：已处理

完成处理时必须填写处理说明。已处理状态不等于用户已获得退款或确认满意。

**验收标准：**

- 创建工单后，正文、工单卡片和后台编号一致。
- 工单可在商家页面查询。
- 重启服务后工单仍存在。
- 状态变更成功后页面和数据库一致。
- 数据写入失败时，不得提示创建成功。

### FR-03：商家运营 Dashboard（P1）

**用户故事：**

作为商家运营人员，我希望通过简单的可视化面板查看客服运行情况，发现高频问题和待处理投诉。

**首版展示指标：**

| 指标 | 定义 |
|---|---|
| 咨询量 | 时间范围内有效的唯一请求数 |
| 独立会话数 | 时间范围内唯一 conversation_id 数 |
| 咨询意图分布 | 商品、订单、物流、投诉等分类 |
| 当前待处理工单数 | 状态为 open 或 in_progress 的工单数 |
| 请求失败率 | 失败或异常中断请求占已完成请求的比例 |
| 响应耗时 | 已记录请求的耗时，展示样本数量 |

**交互要求：**

- 支持按日期查看数据。
- 工单状态可以查看明细。
- 失败请求可以查看错误类别及脱敏的问题文本。
- 演示数据与评测数据明确区分。
- 暂不展示没有可信来源的客户满意度、真实解决率、节省人工成本或销售转化率。

### FR-04：客服数据记录（P1）

系统需记录最小必要的业务事件，用于支持 Dashboard 的真实统计。

建议包括：

- 请求标识及会话标识。
- 请求时间、问题类型。
- 执行成功或失败状态。
- 响应耗时。
- 工单创建和状态变更记录。
- 必要的工具调用结果摘要。

避免存储 API Key、认证信息和不必要的用户个人信息。

### FR-05：AI 产品效果评测（既有成果维护）

复用 Sprint 1 的评测体系，对商品问答、订单查询、退款边界和投诉行为继续回归测试。

保留基线与优化后结果，标记测试模型、样本版本与失败案例。

新增的工单持久化和状态管理功能应使用独立工程测试验证，不把数据库功能通过率混入 LLM 评测准确率。

## 5. 核心业务流程

### 流程 A：商品/订单问答

用户输入问题 → 意图识别 → 检索知识或调用只读查询工具 → 返回有依据的答案。

若信息不足，则要求用户补充信息；若数据不存在，则明确告知无法查询，不编造结果。

### 流程 B：投诉工单

用户提出投诉 → AI 提取必要诉求 → 后端校验字段 → 生成唯一编号并写入数据库 → 告知已记录、待商家处理 → 商家查看工单 → 更新处理状态并填写说明。

### 流程 C：商家运营分析

系统记录咨询与工单事件 → 数据汇总 → 商家打开 Dashboard → 查看问题分布与待处理记录 → 决定是否调整 FAQ、商品描述或处理优先级。

## 6. 页面需求

### 页面一：买家客服聊天页

保留当前聊天界面，增强工单确认状态展示。

### 页面二：商家工单管理页

包括工单列表、状态标签、筛选、详情、处理说明输入和更新状态操作。

### 页面三：商家运营概览页

包括核心指标卡片、问题类型分布、工单状态统计和失败请求明细。

首版采用简洁布局，不追求复杂 UI 动画。

## 7. 非功能需求

- 保持现有前后端基础架构。
- 仅面向单店、本地演示。
- 使用 SQLite 保存工单与最小事件。
- 保持模型 API Key 在后端私有配置。
- 系统异常时显示可理解的错误信息。
- 测试数据不得冒充真实商家生产数据。
- 当前版本不能开放真实用户订单数据的公网访问。

## 8. 成功标准

### 工程验收

- 所有核心页面可访问。
- 创建、查询、更新工单全流程通过。
- 工单刷新及服务重启后仍可查询。
- 工单编号及状态一致。
- Dashboard 指标可从数据库记录复算。
- 现有 36 条客服评测案例完成回归，关键业务约束不出现退化。

### 产品验证

- 邀请测试者按指定任务完成工单创建和处理。
- 记录任务是否完成、遇到的问题和主观体验反馈。
- 根据反馈形成至少一次产品设计迭代。

上述均为拟定验收要求，不代表已完成。

## 9. 优先级与发布范围

| 优先级 | 功能 | 版本 |
|---|---|---|
| P0 | 工单真实保存、唯一编号及状态更新 | Sprint 2 |
| P0 | 不编造退款和人工处理结果 | Sprint 1 已优化，继续回归 |
| P1 | 商家基础 Dashboard | Sprint 2 或后续小版本 |
| P1 | Figma 交互原型、业务验收 | Sprint 2 |
| P2 | AI 解决率、满意度与成本精细化分析 | 后续 |
| 暂不做 | 真实退款、多店 SaaS、完整人工在线客服 | 当前 MVP 之外 |

## 10. 风险与待验证事项

- 未进行真实商家访谈，目标客户痛点和优先级仍属于假设。
- 固定评测集成绩不能代表生产环境表现。
- 当前缺少真实订单权限校验，因此只能使用模拟数据。
- 工单已处理与用户问题真实解决是不同概念。
- 若项目后续公开部署，应重新评估身份认证、依赖安全和数据隐私。
