# 评测与验证证据

## 数据与协议

所有业务案例使用 DemoDataProvider，真实调用历史配置的 `glm-5.3-flash`。案例和评分器位于 `backend/evals`，哈希在各轮 manifest 内；物流评测日期固定为 2026-10-17。案例对开发者可见，不是盲测或独立留出集。

| 目录 | 历史结果 | 时间 |
|---|---|---|
| baseline | 15/36 | 2026-10-17 |
| sprint1-first | 35/36，C02 失败 | 2026-10-17 |
| sprint1-final | 36/36 | 2026-10-17 |
| sprint1-critical | 24/24 | 2026-10-17 |
| sprint2 | 36/36，7 张工单保存 | 2026-10-20 |
| sprint2-critical | 24/24 | 2026-10-20 |

每个目录保留 results.jsonl、summary.json 和 manifest.json。未用更好结果覆盖原始失败轮次。公开版不重复上传每轮源码快照：上游基准提交见 README，当前源码就在仓库中，历史源码清单哈希保留在 manifest。

**必须同时阅读 [BASELINE_REVIEW.json](BASELINE_REVIEW.json)**：原版 5 条存在同义表达误判，仅接受这些表达时敏感性口径为 20/36；这不是独立人工准确率。固定规则对额外无证据承诺也可能漏检。不要仅用 41.7% → 100% 代表真实客服质量。

Sprint 2 通过统一服务运行，来源标记 evaluation；工具名称断言读取该请求真实提交的工具事件，正文及编号取保存后的响应。与直接图评测相比，执行路径包含持久化；模型、案例和评分器保持相同。历史 60 条 evaluation 请求是 36+24 次测试，不能写成 60 个真实客户。
